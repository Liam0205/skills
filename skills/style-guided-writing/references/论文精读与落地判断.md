# 体裁模板：论文精读 + 落地判断

## 什么时候用

读到一篇方法论文，同时想做两件事：讲给没读过的同事听，以及判断它能不能用在自己的场景。这两件事决定了文章必须是**前后两半**，不能揉在一起。

揉在一起的典型症状：开头就讨论「在我们这里该怎么改」，可读者还没看懂论文在做什么，判断没有立足点。

## 骨架

### 前半：讲给没读过的人听

**一、要解决的问题**

先讲动机，再讲已有做法的共性问题。要点：

- 动机要落到具体代价上，并且**明说有几条，然后逐条标号**。
- 已有做法在论文里是要被批判的，措辞不能写成「已有三种成熟方案」。写「过去有三种尝试」。措辞背后的判断是：这三条都不够用，作者才要另起一个。
- 收在「共性问题在于：成本按任务数线性累加」这类一句话上，再引出新方法的学习对象。

**二、具体做法**

机制本身，配一张结构图。要点：

- 先说明核心对象是什么（它由哪些张量组成），再解释**为什么只能是这样**——通常是一条物理约束，不是设计偏好。
- 和相邻方法对照着讲（这里是 prefix-tuning），讲清楚形状相同、来源不同。
- 训练侧改动用「对象：说明」的条目列出来（词表、embedding、输入、mask），不要写成流水短句。
- 讲「为什么这样就能压进去」时，把梯度通道说明白：谁看不见谁、梯度只能从哪儿流回去。不要用「瓶颈由结构强制产生」这类不落地的说法。
- 如果模型结构有两类（decoder-only / encoder-decoder），要单独讲后者多改哪几处，并指出哪一处是缓存成立的前提。

**三、效果评估**

- 先交代数据规模和验证集的构造，读者才知道数字能不能外推。
- **对照组要讲「为什么这样设」，而不只是「设了什么」。** 少一组就分不清是压得太狠还是压的方式不对。
- 数字之后列「值得留意的地方」，逐条标号。
- 效率数字必须先交代参照系（见下）。
- 失败模式给具体例子，不要概括。
- 最后列作者承认的局限，以及**论文自己没做的事**——往往是落地时第一个卡住的地方。

### 后半：换到我们的场景

**四、哪一处变了**

通常是一个量的变化，而这个变化把收益从一根轴换到另一根轴。写作要点：先给出那个量的对比（这里是「前缀占整条序列的比例」，论文约 1%，我们接近 100%），再说明它意味着收益的性质变了。

**五、哪一处没变**

任务性质上的差异。这里是「生成任务吃语义近似，判别任务吃字段精确」。由此推出评估口径的变化（不看平均分，看对全量排序 oracle 的承接率），最后落到起步方案。

## 这个体裁最容易写错的五处

1. **把数据集的统计量当成设计目标。** 「数据集里 prompt 平均 26 个 token」是人工评测集的属性；论文不是因为 26 个 token 才这样设计。写成「为 26 个 token 的 prompt 设计的」是硬伤。
2. **不交代收益数字的参照系。** 「FLOPs 降 40%」是对完全不缓存算的；换成「前缀 KV 已缓存」只剩 0.11%。不交代参照系，读者会高估一个数量级，而且会误以为作者在吹。
3. **只报结果、不报对照组的意义。** TF-IDF 那组对照的价值在于固定住压缩率这个变量，只剩「连续激活 vs 离散 token」一个差异。这一层不写出来，四组对照看起来只是四个数字。
4. **略过「论文没做的事」。** 位置编码、和真正对应的基线没比、大 batch 下收益没有数据——这些不是挑刺，是读者落地时会撞上的地方，属于这篇精读最有价值的部分。
5. **前半写成综述。** 如果前三节读完，读者只记住了论文的结构而不记得它到底解决了谁的什么问题，说明写成了 survey。

## 后半最容易写错的技术判断（2026-11 gist 稿复盘）

前半照论文核对数字通常不出错，错误集中在论文和自己场景的衔接处。重写前逐条查：

1. **收益要按两种参照系各算一遍。** 论文的参照系（「前缀 KV 已缓存」）和我们今天的真实做法（每次全量重算）往往不同。只用论文的参照系，会写出「省算力基本没有」这种错误结论；正确说法是「省算力的是缓存本身，压缩的作用是让缓存存得下」。
2. **缓存 K 已经带着位置。** RoPE 在写入缓存前已经旋转过，推理时只平移后半段等于改了相对距离。所以 query 必须保持训练时的绝对起点（例如 $j+k+1$），或者训练时把压缩位置固定在同一段。「整体平移不变」只在两边一起平移时成立。
3. **容量要按「每个位置 × 层数 × 头数 × 维度」算，而且要和论文的模型规模对比。** 每个 gist 位置在每一层都有完整的 K/V，容量随 $k$ 线性增长；不要写「k 个 gist 只靠位置区分，所以加 k 没用」。论文用 7B MHA，小模型加 GQA 时单位置容量可能只有它的几十分之一，这才是「k 不敏感」不能照搬的原因。
4. **讨论里用户已经定下的决定必须进稿。** 例如「压 item 而非 query」「固定 k 不分档」「上线是新旧模型版本切换，缓存不单独放量」「半压给精排、全压给粗排」。稿子里漏掉或写成相反立场，等于没听讨论。动笔前把当时对话里用户纠正过的结论列成清单逐条对照。
5. **评估口径的参考答案要写对。** 参考答案是 item 和 query 都不压的全量交叉编码器，不是「不压 query 的排序」。
6. **推测要标出来。** 论文没解释的现象（例如 TF-IDF 低于负控）写成「我的推测是……」，不要当论文结论写。

## 交付

先写前半三节给作者看。语感确认了再写后半。前半的语感不对，后半写得再好也没有立足点。
